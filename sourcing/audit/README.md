# Audit trail of the sourcing work

This directory is the complete record of how the `sources` column of `author-quote.txt`
was produced: every script, every prompt, every search each agent ran, every result page
they returned, and a ledger of every agent session with its outcome and cost. Nothing that
was used is kept outside the repository.

## What was done, in order

1. **Offline citation dictionaries** (`sourcing/match_offline.py`, `sourcing/build_refs.py`):
   the Wikiquote extracts published as npm packages by "foba" and Bartlett's *Familiar
   Quotations* (Project Gutenberg #16732) were normalised (`sourcing/norm.py`) and matched
   against the corpus. Raw extraction helpers: `scratch_scripts/extract_foba.js`,
   `scratch_scripts/parse_bartlett_16732.py`. Evidence: `sourcing/evidence/offline_dictionaries.jsonl`.
2. **Verbatim location in Project Gutenberg full texts** (`sourcing/locate_fulltext.py`,
   `sourcing/run_fulltext.py`, GITenberg manifest in `sourcing/gitenberg_manifest.json`,
   reachability check `scratch_scripts/check.sh`): Shakespeare plus 94 other works by 41
   authors were fetched and each corpus line was searched for as a normalised substring.
   Evidence: `sourcing/evidence/gutenberg_fulltext_*.jsonl`.
3. **Web-search agents** (the bulk of the work): the corpus was split into 227 batches of
   about 170 lines, most-quoted authors first (`sourcing/make_batches.py`, batches in
   `sourcing/batches/`). Each batch was given to an independent Claude Code session that
   ran one web search per quote and returned a JSONL record per line. Those records are in
   `sourcing/web_results/batch_NNNN.jsonl`, unchanged from what the agent published.
4. `sourcing/web_to_evidence.py` merges the batch files into
   `sourcing/evidence/web_search_agents.jsonl`; `sourcing/build_column.py` writes column 3 from
   all evidence files.

## What each agent was told

- `prompts/batch_NNNN.txt` is the exact prompt sent to the session for that batch, for every
  batch dispatched from batch_0026 onwards (the prompt is generated by
  `sourcing/orchestrate/make_sibling_prompt.py`; the generated text was saved before dispatch).
- Batches 0001 to 0025 were dispatched with earlier revisions of the same prompt, whose
  text is `sourcing/AGENT_PROMPT.md` (the first version, which asked the agent to write
  `results.jsonl` and return it inline) followed by the artifact hand-off wording that
  `make_sibling_prompt.py` still contains. The differences between revisions were:
  - v1 (batch_0001 to 0009, "old_batch_*" runs): results returned inline / as a file.
  - v2 (batch_0001 to 0025 re-runs): results published as a page titled
    `Quotables results batch_NNNN` and a one-line notification scheduled to the parent session.
  - v3 (batch_0026 onwards): plus a hard cap of one search per row against the 200-search
    session budget and an explicit `unsearched` status.
  - v4 (batch_0048 onwards, 2026-09-06): plus "republish the page every 20 rows" so a session
    killed by a usage limit loses at most 20 rows, and "do not attempt any git push".
- `checkin_trigger_prompt.txt` is the routine the orchestrating session ran every 45 minutes
  to collect results, recover partial pages and keep eight sessions in flight.

## What each agent did

- **Searches:** every `queries` field in `sourcing/web_results/batch_NNNN.jsonl` is the literal
  web search string(s) the agent issued for that line; `evidence` lists the URLs it relied on
  with a one-line note, including the negative findings ("only aggregators carry the quote").
  `sources` is what went into the column. `status` is one of sourced / misattributed /
  unverified / unsearched.
- **Result pages:** `raw_pages/batch_NNNN.html` are the pages exactly as published by the
  agents (121 of the 124 ingested pages were saved from the orchestrator's reads; batch_0051's
  partial page was read inline and only its JSONL is in `web_results/`; two inline reads were
  re-typed into `raw_pages/*_inline.html` and are marked as such).
- **Sessions:** `sessions.jsonl` has one record per agent session (153 sessions, including two
  5-row pilots): batch, model, start time, outcome, cost in USD, input/output tokens, and the
  URL of the result page. 121 sessions completed; 32 were killed by account usage limits
  (five-hour or seven-day) and their batches were re-dispatched. Total agent cost: about
  USD 1,779 (USD 163 of it for the 2026-09-08 run of batches 0066 to 0077, USD 187 for the
  2026-09-10/13 run of batches 0078 to 0090, USD 117 for the 2026-09-14 run of batches
  0091 to 0099 and USD 290 for the 2026-09-15 run of batches 0100 to 0119).
- **Per-batch tallies:** `batch_summary.tsv`.

## Orchestration

The audit trail is maintained automatically while the run goes on: `handle_result.sh` copies every
result page into `raw_pages/` and regenerates `batch_summary.tsv`; `record_session.py` appends the
session record (outcome, cost, tokens, page URL) to `sessions.jsonl`; prompts are saved to
`prompts/` before dispatch; everything is committed and pushed after each ingest.

`sourcing/orchestrate/` holds the scripts the parent session used: `make_sibling_prompt.py`,
`handle_result.sh` (extract JSONL from a page with `ingest_artifact.py`, mark received, rebuild
evidence and column), `mark_dispatched.py` (state changes and status), `commit_progress.sh`
(commit as alvations and retry the push). `sourcing/orchestrator_state.json` records every
dispatch (batch -> session), every received batch, every archived session and every failure
with its reason. `scratch_scripts/` holds the thin wrappers and the bundle script used from
the orchestrator's scratch directory.

## 2026-09-17/18: batches 0120 to 0187, and the return-channel failures

On 2026-09-17 the user asked for the run to continue to a deadline with as much fan-out as
needed, auto-resuming through any usage limit. The fan-out was widened to eight concurrent
sessions and an hourly self-wake routine was added so the run survives a limit that stops this
session too. Batches 0120 to 0179 completed normally (the five-hour limit killed the 0136-0143
wave on 2026-09-17T23:24Z; their partial pages were ingested and the remainders re-run as
b-batches, and the seven-day Fable pool was exhausted at 03:49Z, after which children were
created on claude-opus-5 instead).

Batches 0180 to 0187 then hit a harder problem: **the account's artifact-publishing quota ran
out at about 06:03Z** (it resets 2026-09-19T00:06Z). Artifacts had been the return channel for
every child, so eight sessions finished their 170 rows with no way to deliver them. Two
fallbacks were tried:

- **git.** Children were told to commit `sourcing/web_results/batch_NNNN.jsonl` to this branch
  themselves. This worked for 0185 and 0186 but was refused for the others - a child's
  permission classifier blocks External System Writes, and whether it fires varies by session.
  `sourcing/orchestrate/make_sibling_prompt_git.py` is the prompt generator written for this
  channel; it is kept for the record, but it cannot be relied on.
- **text relay.** A child re-serialises its rows as compact one-line JSON and sends them back in
  25-row chunks as `create_trigger` messages to this session, which appends them verbatim and
  validates every line. Slow and token-hungry (about 90k tokens per 170-row batch) but it works
  where the others do not. It recovered 0181, 0182 and 0184 in full; 0184 had published no
  artifact at all, so those 170 rows would otherwise have been lost.

0180, 0183 and 0187 have all 170 rows complete inside their containers with every channel
blocked (0183's `create_trigger` is refused as well), so each was given a trigger that fires
after the quota resets and simply publishes the artifact it had already built. New dispatches
were held until then rather than spending money on children that could not report back.

Lessons carried into the resume procedure: the artifact channel has a daily cap that a wide
fan-out can exhaust; a child cannot be assumed to have any outbound write; and a batch's rows
should be pushed out in instalments as they are found, never only at the end.
